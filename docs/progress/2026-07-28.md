## 3. 主要代码改进

本次修改集中在以下三个文件：

```text
src/llm/note-pipeline.ts
src/llm/gemini-client.ts
tests/note-pipeline.test.ts
```

### 3.1 重复批注压缩

新增 Evidence 压缩逻辑，按照附件、页码、批注类型、原文内容和高亮内容识别同一来源位置。

同一位置上的重复批注不再逐条发送给模型，而是：

- 保留一个代表性 Evidence；
- 合并不同的用户评论；
- 去除 `[AI压力测试 001/083]` 一类序号前缀；
- 合并标签；
- 保持不同原文位置之间的边界。

自动测试中的 101 条模拟批注可以压缩为 15 个不同来源位置。这样既保留了用户真实关注点，又显著减少了模型输入中的机械重复。

### 3.2 用户问题识别与去重

原来的判断方式容易把任何包含“为什么”的评论都视为问题。例如：

```text
需要结合上下文解释为什么深度能够改善分类效果，同时区分原文与后续解释。
```

这实际上是生成要求，不应强制出现在“待验证问题”中。

现在的问题识别改为：

- 优先识别以问号结尾的句子；
- 识别以“为什么、如何、是否、能否”等疑问词直接开头的句子；
- 从长评论中提取独立疑问分句；
- 对重复问题建立指纹并合并关联批注 ID；
- 不再把嵌在陈述性要求中的疑问词机械地判为独立问题。

### 3.3 语义等价问题校验

实机生成中，模型已经把三个用户问题以语义等价的方式保留在“待验证问题”中，但旧校验器依赖精确文本或内部映射，仍误报其中三个问题缺失。

本次增加了轻量的语义可见性匹配：

- 先进行规范化和包含关系判断；
- 再通过字符二元片段重叠判断问题是否等价；
- 同时检查后台 `open_question` 映射和最终 Markdown 中可见的问题；
- 对重复出现的同一个问题只要求保留一次。

这使校验器能够接受合理改写，同时继续拦截真正被省略或被改写为确定结论的问题。

### 3.4 审查阶段稳定性优化

此前长批注实机测试中，笔记主体能够生成，但事实审查请求连续两次在约 126 秒后返回 HTTP 524。

根因主要是审查任务同时要求模型：

- 修订完整笔记；
- 为每条内容映射重复输出审查结果；
- 返回大量 Evidence ID 和解释；
- 在长批注输入下生成体积很大的 JSON。

本次将审查输出简化为：

- 模型内部完成逐条检查；
- 只返回修正后的 `final_note`；
- 不再要求重复输出完整审查清单；
- 审查请求的最大输出限制为 8192 tokens；
- 最终结构、Evidence ID、数字和问题保留继续由本地规则校验。

真实压力测试中，审查请求不再出现 524。第一次审查后仍发现一个真正遗漏的问题，系统自动进入再次修订，最终显示“生成并校验通过”。

### 3.5 审查映射 ID 修复

部分兼容模型会正确返回审查项，但把 `mapping_id` 留空。过去这会让已经得到支持的内容在本地校验时被判为缺少审查。

现在仅在以下安全条件下自动修复：

- 空白审查项数量与缺失映射数量完全一致；
- 优先按照有效 Evidence ID 的唯一重叠关系配对；
- 无法唯一判断时只在剩余项一一对应的条件下顺序补齐；
- 不满足条件时保持失败，不进行猜测性映射。

### 3.6 Gemini 客户端输出上限

`GeminiClient.generateJson()` 新增可选的 `maxTokens` 参数，用于给不同任务设置合理的输出上限。当前只在审查校正任务中使用 8192 tokens，其他调用保持原有行为，避免扩大改动范围。

## 6. API Key 问题复盘

### 表面现象

重新构建并安装插件后，连接服务一度失败，因此看起来像 API Key 被清空。

### 实际原因

代码和实机状态共同证明，构建过程没有删除 API Key：

- API Key 由 Zotero/Firefox 的 `Services.logins` 凭据库保存；
- 凭据使用固定 origin 和 realm，与 XPI 文件内容分离；
- `install()` 和 `uninstall()` 回调只记录日志，不清除凭据；
- 只有用户明确执行“清除 API Key”时才调用删除逻辑；
- 设置界面重新打开后仍显示“API Key 已保存”；
- 后续连接测试成功，并完成了真实模型调用。

因此本次没有创建明文 API Key 文件，也没有把 Key 写入源码、`.env` 或安装包。

### 最终方案

继续使用 Zotero 自带凭据库是当前更方便且更安全的方式：

- 不进入 Git；
- 不进入 XPI；
- 不因普通重建或升级而变化；
- 不需要额外维护本地秘密文件路径；
- 减少明文泄露和误上传风险。

此次连接失败更可能来自短时网络或服务可用性问题，而不是凭据被删除。后续如果再次出现类似现象，应先区分“凭据不存在”和“凭据存在但服务连接失败”，不要直接要求用户重新填写 Key。

## 7. 今天遇到的主要困难与解决方式

### 困难一：长批注让请求体和审查输出同时膨胀

**现象：** 101 条批注中存在大量相同来源位置和重复结构化评论，审查阶段发生 HTTP 524。

**解决：** 在模型调用前按来源位置压缩 Evidence，合并不同评论；审查阶段只返回修订后的笔记，并限制最大输出长度。

### 困难二：问题已出现在笔记中，校验器仍认为缺失

**现象：** 模型合理改写了用户问题，但内部 `open_question` 映射不完整，精确匹配产生误报。

**解决：** 同时检查后台映射和 Markdown 可见问题，并加入保守的语义等价判断。

### 困难三：真正的问题被直接回答，没有先保留疑问形式

**现象：** 关于历史意义的问题被模型直接写成解释性结论，违反“用户问题必须保留”的产品规则。

**解决：** 将具体校验错误传给修订阶段，并明确要求被点名的问题必须先建立 `open_question` 映射、保持疑问形式，之后才可以补充当前证据范围内的解释。

### 困难四：包含疑问词的生成要求被误判为问题

**现象：** “需要解释为什么……”一类陈述性指令被要求写入待验证问题。

**解决：** 从“包含疑问词”改为“识别直接疑问句和独立疑问分句”。

### 困难五：审查项缺少 `mapping_id`

**现象：** 模型返回了完整审查内容，但部分映射 ID 为空，导致本地一致性检查失败。

**解决：** 仅在数量完全匹配、Evidence 重叠关系足够明确时进行确定性补齐，否则继续报错。

### 困难六：实机菜单自动化不稳定

**现象：** Zotero 条目右键菜单中的“AI 整理批注”有时只被选中，没有真正触发；使用键盘导航时还可能误打开 PDF 或其他插件。

**解决：** 每次操作前重新读取当前界面状态，使用条目右键菜单的实时可访问性元素直接点击“AI 整理批注”，不再依赖固定索引或 `End`、`Return` 组合。

### 困难七：服务连接异常容易被误认为 API Key 丢失

**现象：** 短时连接失败与缺少 API Key 在用户感知上相似。

**解决：** 检查设置界面的凭据保存状态、凭据存储代码和真实连接结果，确认是连接波动而不是构建清除凭据。
